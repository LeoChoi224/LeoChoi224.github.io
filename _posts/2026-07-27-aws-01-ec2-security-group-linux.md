오늘부터 3일 동안은 배포를 배운다. 지금까지 만든 FastAPI 백엔드와 React 프런트엔드는 전부 내 컴퓨터에서만 돌았다. `http://127.0.0.1:8000`은 나만 열 수 있는 주소라서, 남에게 보여주려면 꺼지지 않고 인터넷에 연결된 컴퓨터가 필요하다.

내 노트북을 24시간 켜두고 공인 IP를 받는 것도 이론상은 되지만, 전기, 인터넷, 보안, 고정 IP를 전부 직접 챙겨야 한다. 그런 컴퓨터를 시간 단위로 빌려주는 게 AWS의 EC2다.

## 3일 동안 만들 전체 그림
3일이 하나의 그림을 향해 간다. 먼저 봐두면 각 단계가 어디에 들어가는지 알 수 있다.

```
사용자 브라우저
   │  https://example.com          ← 화면 (React 빌드 결과물)
   │  https://api.example.com/...  ← API 요청
   ▼
[DNS] 도메인을 알맞은 곳으로 안내
   ├─ example.com      → CloudFront
   └─ api.example.com  → EC2 탄력적 IP

[CloudFront] (CDN + HTTPS)                     ← 7/29
   └─ OAC ──▶ [S3] React 정적 파일

[EC2] (Nginx 443 + Let's Encrypt 인증서)        ← 7/28~29
   └─ Gunicorn → Uvicorn → FastAPI
         ├─ [RDS] MySQL
         └─ [S3] 업로드 파일
```

도메인은 예시 주소로 바꿔 적었다. 오늘은 이 그림에서 EC2 한 칸을 켜고, SSH로 들어가서 FastAPI를 하나 띄워보는 데까지 했다.

## 클라우드는 결국 남의 컴퓨터다
AWS는 전 세계에 거대한 컴퓨터실을 지어두고, 그 안의 컴퓨터를 시간 단위로 쪼개서 빌려준다. EC2 인스턴스를 하나 만든다는 건 "리눅스가 깔린 컴퓨터 한 대를 지금부터 빌린다"는 뜻이고, 요금은 켜둔 시간만큼 나간다.

그래서 로컬에서 하던 일(파이썬 설치, 패키지 설치, 코드 실행)을 거기서 그대로 다시 해야 한다. 클라우드라고 알아서 해주는 건 없다.

## 리전과 가용영역
AWS 리소스는 전부 어느 **리전(지역)** 안에 만들어진다. 수업은 서울 리전으로 고정했다.

| 용어 | 뜻 |
|---|---|
| 리전(Region) | 물리적으로 떨어진 지역 단위. 서울은 `ap-northeast-2` |
| 가용영역(AZ) | 한 리전 안의 독립된 데이터센터. 서울은 `2a`, `2b`, `2c`, `2d` |

리소스를 만들 때마다 콘솔 오른쪽 위의 리전이 서울인지 확인해야 한다. 다른 리전에 만들면 목록에 안 보여서 "분명히 만들었는데 사라졌다"가 된다.

가용영역이 여러 개인 이유는 한 데이터센터에 화재나 정전이 나도 다른 곳은 살아 있게 하려는 것이다. 그래서 RDS를 만들 때 "서브넷이 최소 2개 AZ에 걸쳐 있어야 한다"는 조건이 붙는다. 혼자 하는 실습에서는 크게 신경 쓸 일이 없지만, 콘솔이 자꾸 물어보니 뜻은 알아둬야 한다.

그리고 모든 서비스가 리전에 속하는 건 아니다. IAM(권한)과 CloudFront는 전 세계 공통 서비스이고, S3 버킷은 리전에 만들지만 이름은 전 세계에서 겹치면 안 된다. 그래서 버킷 이름 뒤에 고유한 값을 붙였다. 7/29에 만날 예외도 하나 있는데, CloudFront에 붙일 인증서는 버지니아 리전(`us-east-1`)에서만 만들 수 있다.

## EC2 인스턴스를 켤 때 정하는 것
콘솔에서 **Launch instance**를 누르면 이것저것 물어보는데, 실제로 정할 건 몇 개 안 된다.

### AMI - 어떤 운영체제로 시작할까
AMI(Amazon Machine Image)는 컴퓨터를 처음 켤 때 넣는 설치 디스크 같은 것이다. 수업은 **Ubuntu Server 24.04 LTS**를 골랐다.

```
Ubuntu        → 사용자 계정 ubuntu,   패키지 명령 apt
Amazon Linux  → 사용자 계정 ec2-user, 패키지 명령 dnf
```

이 차이가 이후 모든 명령에 따라다닌다. 인터넷 예제에서 `ec2-user`가 나오면 Amazon Linux 기준이라는 뜻이니 `ubuntu`로 바꿔 읽으면 된다.

LTS는 Long Term Support(장기 지원)다. 우분투는 2년마다 LTS 버전을 내고 5년 동안 보안 업데이트를 준다. 그 사이에 나오는 버전은 지원 기간이 9개월뿐이라, 도중에 지원이 끊기면 곤란한 서버에는 LTS를 쓴다.

### 인스턴스 타입 - 얼마나 좋은 컴퓨터를 빌릴까
`t3.micro`를 골랐다. 이름을 읽는 법이 있다.

```
t3.micro
│ │  └── 크기 (nano < micro < small < medium < large ...)
│ └───── 세대 (숫자가 클수록 최신)
└─────── 계열 (t = 범용·버스트형, m = 범용, c = 연산, r = 메모리)
```

`t3.micro`는 vCPU 2개에 메모리 1GB 정도이고, 프리 티어(무료 사용량) 대상이라 실습용으로 쓴다. `t` 계열은 버스트형이라 평소에는 CPU를 적게 쓰면서 크레딧을 모아두고, 필요할 때 몰아 쓰는 방식이다. 실습이나 개인 프로젝트에는 충분하지만, CPU를 꾸준히 많이 쓰는 서비스에는 `m` 같은 다른 계열이 맞다.

### 키페어 - 어떻게 들어갈까
키페어를 만들면 `.pem` 파일을 내려받는다. 이게 그 서버에 들어가는 유일한 열쇠이고, **잃어버리면 다시 받을 수 없다.**

비밀번호 대신 열쇠 파일로 로그인하는 방식이다. AWS는 짝이 되는 공개키만 서버에 심어두고, 접속할 때 내 `.pem`(비밀키)과 맞춰본다. 인터넷에 열린 서버에는 비밀번호를 자동으로 찍어보는 봇이 끊임없이 들어오기 때문에, 클라우드 서버는 기본적으로 비밀번호 로그인을 꺼두고 키만 허용한다.

### 보안 그룹, 그리고 IAM 역할
보안 그룹은 어느 문을 열어둘지 정하는 방화벽이다. 오늘의 핵심이라 아래에서 따로 정리했다.

하나 더 놓치기 쉬운 게 **IAM instance profile**이다. **Advanced details**를 펼쳐야 나오는 항목이라 그냥 지나치기 쉽다. 내일 만드는 IAM 역할을 여기에 붙인다.

## IP 두 개와 탄력적 IP
EC2 하나에는 IP가 두 개 붙는다.

| 종류 | 예 | 누가 쓸 수 있나 |
|---|---|---|
| 프라이빗 IP | `172.31.x.x` | AWS 내부(같은 VPC)에서만 |
| 퍼블릭 IP | `x.x.x.x` 형태의 공인 주소 | 인터넷 어디서나 |

프라이빗 IP는 사내 내선번호, 퍼블릭 IP는 밖에서 걸 수 있는 대표번호라고 생각하면 된다.

그런데 기본으로 받는 퍼블릭 IP에는 곤란한 성질이 있다. **인스턴스를 중지했다가 다시 켜면 퍼블릭 IP가 바뀐다.** 도메인을 이 IP에 연결해뒀다면 그 순간 서비스가 끊긴다. 그래서 고정 주소인 **탄력적 IP(Elastic IP)**를 따로 받아서 붙인다.

```
EC2 콘솔 → Network & Security → Elastic IPs
  → Allocate Elastic IP address                              (주소 하나 받기)
  → Actions → Associate Elastic IP address → 인스턴스 선택     (인스턴스에 붙이기)
```

이렇게 하면 인스턴스를 껐다 켜도 주소가 그대로다.

요금은 조심해야 한다. 예전에는 실행 중인 인스턴스에 붙어 있는 탄력적 IP가 무료여서 "붙어 있으면 무료, 놀고 있으면 과금"이라고 설명하는 글이 많다. 그런데 AWS는 2024년 2월부터 퍼블릭 IPv4 주소마다 시간당 요금을 받는다. 지금은 붙어 있어도 요금이 계산되고(프리 티어 혜택 안에서는 무료로 처리될 수 있다), 아무 데도 안 붙은 탄력적 IP도 계속 요금이 나간다. 그래서 실습이 끝나면 인스턴스만 지우고 끝내지 말고 탄력적 IP를 **Release**까지 해야 한다.

## 보안 그룹 - 기본은 전부 차단
오늘 배운 것 중 가장 중요한 부분이다. 보안 그룹은 서버 앞에 세운 경비원 같은 것인데, "누가(Source) 어느 문(Port)으로 들어올 수 있는지"를 적은 명단을 들고 있다.

가장 중요한 성질은 **기본이 전부 차단이고, 명단에 적은 것만 통과한다**는 것이다. 그래서 막는 규칙은 쓸 필요가 없고 열 것만 적으면 된다. 접속이 안 되면 닫혀 있는 것이고, 열려 있으면 내가 연 것이다.

### 백엔드 서버용 sec-group-ec2

| Type | Port | Source | 이유 |
|---|---|---|---|
| HTTP | 80 | `0.0.0.0/0` (누구나) | HTTP로 들어온 사람을 HTTPS로 넘기고, Let's Encrypt 인증에도 쓴다 |
| HTTPS | 443 | `0.0.0.0/0` (누구나) | 실제 서비스 트래픽 |
| SSH | 22 | **My IP** | 서버에 로그인하는 문이라 나만 |

`0.0.0.0/0`은 "모든 IP"라는 뜻이다. 22번을 `0.0.0.0/0`으로 열면 현관문을 활짝 열어두는 것과 같아서, 콘솔 드롭다운에서 **My IP**를 골라 지금 내 IP만 허용한다.

결국 HTTPS로 쓸 건데 80번까지 여는 이유는 두 가지다.

1. 사용자가 `http://`로 들어와도 받아서 `https://`로 돌려보내야(redirect) 한다. 80이 닫혀 있으면 그 사람은 접속 실패만 본다.
2. Let's Encrypt가 "이 도메인이 정말 이 서버인가"를 80번 포트로 확인한다. 닫혀 있으면 인증서를 못 받는다.

IP가 건물 주소라면 포트는 몇 호인지에 해당한다. 같은 주소로 와도 문마다 다른 서비스가 기다린다.

| 포트 | 용도 |
|---|---|
| 22 | SSH, 원격 접속 |
| 80 | HTTP, 암호화 안 된 웹 |
| 443 | HTTPS, 암호화된 웹 |
| 3306 | MySQL |
| 8000 | 우리 FastAPI (밖에는 열지 않는다) |

80, 443, 22, 3306은 널리 약속된 번호라서 `https://주소`라고만 써도 브라우저가 알아서 443으로 간다. 8000번은 일부러 열지 않는다. 바깥 요청은 Nginx가 80/443으로 받아서 안쪽의 8000번으로 넘겨주게 하는 게 내일 할 설계다.

### 데이터베이스용 sec-group-rds

| Type | Port | Source |
|---|---|---|
| MYSQL/Aurora | 3306 | `sec-group-ec2` (보안 그룹 자체를 지정) |

여기가 오늘 가장 영리하다고 느낀 부분이다. **Source에 IP 대신 다른 보안 그룹을 넣을 수 있다.** "이 IP에서 오는 걸 허용"이 아니라 "`sec-group-ec2` 명찰을 단 것만 허용"이라는 뜻이다. 우리 EC2에 그 명찰이 붙어 있으니 DB에 들어갈 수 있고, 인터넷의 나머지는 3306번에 닿지도 못한다.

IP로 적지 않는 이유는 EC2의 IP가 바뀌면 규칙을 매번 고쳐야 하고, 서버를 여러 대로 늘리면 IP를 전부 적어야 하기 때문이다. 보안 그룹으로 지정하면 "이 그룹에 속한 것 전부"라서 서버가 늘어도 규칙을 건드릴 필요가 없다. 웹 → 앱 → DB처럼 계층을 나눌 때 쓰는 기본 방식이다.

여기에 RDS를 만들 때 **Public access: No**까지 걸면 데이터베이스는 인터넷에서 아예 접근할 수 없는 상태가 된다.

### VPC는 기본 VPC를 그대로
VPC는 AWS 안에 나만 쓰는 가상의 사설 네트워크다. 계정을 만들면 리전마다 기본 VPC가 이미 있어서 수업에서는 그걸 그대로 썼다. 서브넷이나 라우팅 테이블 같은 건 기본 VPC를 쓰는 동안은 몰라도 되고, 지금은 이 정도만 알아두면 된다.

- 퍼블릭 서브넷: 인터넷과 통하는 자리. EC2를 여기에 둔다.
- 프라이빗 서브넷: 인터넷과 안 통하는 자리. 원래 DB는 여기에 둔다.

우리는 기본 VPC에 Public access: No와 보안 그룹을 조합해서 비슷한 효과를 냈다.

## SSH로 접속하기
인스턴스가 켜지면 SSH로 들어간다.

```bash
ssh -i "myapp-key.pem" ubuntu@<탄력적 IP>
```

| 조각 | 뜻 |
|---|---|
| `ssh` | Secure Shell. 원격 컴퓨터에 암호화된 연결로 로그인한다 |
| `-i "myapp-key.pem"` | identity file. 이 열쇠 파일로 인증한다 |
| `ubuntu` | 로그인할 계정 이름 |
| `@<탄력적 IP>` | 접속할 주소 |

여기서 제일 많이 막히는 게 계정 이름이다. AMI마다 다르다.

| AMI | 계정 |
|---|---|
| Ubuntu | `ubuntu` |
| Amazon Linux | `ec2-user` |
| Debian | `admin` |

그리고 SSH는 비밀키 파일을 남이 읽을 수 있는 상태면 접속을 아예 거부한다. 열쇠를 아무나 볼 수 있는 곳에 뒀다는 뜻이라서다. 맥에서는 `UNPROTECTED PRIVATE KEY FILE!`이라는 무서운 에러가 뜨는데, 권한을 나만 읽기로 바꾸면 끝이다.

```bash
chmod 400 myapp-key.pem      # 맥/리눅스: 나만 읽을 수 있게
```

윈도우는 파일 속성 → 보안 → 고급에서 상속을 끄고 본인 계정만 남기면 된다. 접속을 끊을 때는 `exit`이나 `Ctrl + D`다.

들어가면 검은 화면에 한 줄만 있다. 리눅스 서버에는 화면도 마우스도 파일 탐색기도 없어서, 지금부터는 전부 명령으로 시켜야 한다.

```
ubuntu@ip-172-31-12-34:~$
│       │                │
│       │                └── 현재 위치 (~ = 홈 디렉터리 = /home/ubuntu)
│       └─────────────────── 이 컴퓨터의 이름 (프라이빗 IP가 들어간다)
└─────────────────────────── 지금 로그인한 사용자
```

프롬프트 끝이 `$`면 일반 사용자이고 `#`면 root(최고 권한)다. 인터넷 예제에서 `# apt install ...`처럼 `#`로 시작하는 줄은 "root로 실행하라"는 뜻이라서, 우리는 앞에 `sudo`를 붙여서 친다. `#`까지 그대로 복사해서 붙이면 주석이 돼서 아무 일도 안 일어난다.

## apt로 설치하기
빌린 컴퓨터는 빈 컴퓨터다. git, nginx, 파이썬까지 직접 깔아야 한다.

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y git nginx
```

| 명령 | 하는 일 |
|---|---|
| `apt update` | 설치할 수 있는 패키지 목록을 새로 받아온다 (설치는 안 한다) |
| `apt upgrade` | 이미 깔린 패키지를 최신으로 올린다 |
| `apt install 이름` | 새로 설치한다 |
| `-y` | "계속할까요? [Y/n]"를 묻지 않고 예로 진행한다 |

`apt update`는 카탈로그를 새로 받는 것이고 `apt install`은 카탈로그를 보고 주문하는 것이다. 카탈로그가 낡으면 `E: Unable to locate package`(그런 물건 없음)가 나온다. 새 서버에서 첫 설치가 실패하는 원인 대부분이 이것이다.

`&&`는 앞 명령이 성공했을 때만 뒤 명령을 실행한다. `update`가 실패하면 `upgrade`는 아예 돌지 않는다.

`sudo`는 "이 명령 하나만 관리자 권한으로 실행"이다. 패키지 설치, `/etc` 아래 설정 파일 편집, 서비스 재시작처럼 시스템 전체에 영향을 주는 일에는 `sudo`가 필요하다. 반대로 내 홈 디렉터리(`/home/ubuntu`) 안에서 하는 `git clone`, 가상환경 만들기, 코드 수정에는 붙이지 않는다. `sudo`로 만든 파일은 주인이 root가 돼서 나중에 일반 권한으로 고칠 수 없게 된다.

인터넷 예제에는 `apt-get install`도 자주 보이는데 거의 같은 일을 한다. `apt`는 사람이 쓰기 편하게 만든 쪽(진행률 표시 등)이라 손으로 칠 때는 `apt`, 스크립트에는 `apt-get`을 쓰는 게 관례다.

## 파이썬은 uv로 설치하기
```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
source $HOME/.local/bin/env
uv --version

uv python install 3.12.5
```

첫 줄의 `curl` 옵션을 뜯어보면 이렇다.

| 옵션 | 뜻 |
|---|---|
| `-L` | 리다이렉트를 따라간다 |
| `-s` | 진행률 표시 없이 조용히 받는다 |
| `-S` | 단, 에러는 보여준다 |
| `-f` | HTTP 에러면 실패로 처리한다 |

`|`(파이프)는 앞 명령의 결과를 뒤 명령의 입력으로 넘긴다. 그래서 첫 줄은 "설치 스크립트를 받아서 곧바로 셸에 넘겨 실행하라"는 뜻이다. 그다음 `source $HOME/.local/bin/env`는 방금 설치한 `uv`의 위치를 지금 셸에 알려주는 것이다. 이걸 빼먹으면 설치는 됐는데 셸이 못 찾아서 `uv: command not found`가 난다. 새 터미널을 열어도 된다.

### 왜 apt로 파이썬을 안 까나

| 방법 | 패치 버전 고정 | 특징 |
|---|---|---|
| **uv** | 가능 (3.12.5를 딱 집어서) | 미리 만들어진 파일을 받아와서 빠르다 |
| apt + deadsnakes PPA | 불가 (3.12의 최신 패치만) | 시스템 파이썬으로 설치된다 |
| pyenv | 가능 | 소스를 컴파일해서 느리고 빌드 도구가 많이 필요하다 |

우분투 저장소는 "3.12 중에 저장소가 정한 버전"만 주는데, 우리는 개발 PC와 똑같은 **정확히 3.12.5**가 필요했다. 개발 PC와 서버의 파이썬 버전이 미묘하게 다르면 "내 컴퓨터에선 됐는데" 문제가 생긴다.

가상환경도 uv로 만든다.

```bash
uv venv --python 3.12.5 .venv
source .venv/bin/activate
uv pip install -r requirements.txt
```

`uv venv`로 만든 가상환경에는 기본으로 `pip`가 들어 있지 않다. 그래서 패키지는 `uv pip install`로 깔고, 꼭 `pip`가 필요하면 만들 때 `uv venv --seed`를 붙인다.

그리고 가상환경 없이 시스템 파이썬에 `pip install`을 하려고 하면 `externally-managed-environment` 에러가 난다. 시스템 파이썬을 건드리면 OS 도구들이 깨질 수 있어서 우분투가 전역 설치를 막아둔 것이다(PEP 668). 가상환경을 쓰라는 뜻이다.

## 파일 다루기
배포하면서 실제로 쓴 명령만 모으면 이 정도다.

```bash
pwd                      # 지금 어디에 있나
ls -al                   # 파일 목록 (-a 숨김 파일 포함, -l 자세히)
cd ~/UpDown/backend      # 이동 (~ 홈, .. 상위, - 직전 위치)
cat requirements.txt     # 파일 내용을 화면에 출력
mkdir -p a/b/c           # 디렉터리 생성 (-p 중간 경로까지 한 번에)
cp .env.example .env     # 복사
rm -f 파일               # 삭제 (-f 파일이 없어도 에러를 내지 않음)
ln -s 원본 링크위치       # 심볼릭 링크 = 바로가기
```

`ln -s`는 내일 Nginx 설정에서 꼭 나온다.

```bash
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/
```

윈도우의 바로가기와 같다. 원본은 한 곳에 두고 다른 곳에서 그걸 가리키게 한다. Nginx는 `sites-available`(보관함)에 설정 파일을 두고, `sites-enabled`(켜진 목록)에 링크를 걸어서 켜고 끄는 방식을 쓴다.

이름이 `.`으로 시작하는 파일은 숨김 파일이라 그냥 `ls`에는 안 보인다. `.env`, `.venv`, `.git`이 전부 그렇다. `ls -a`를 써야 보인다.

서버에는 VS Code가 없으니 파일은 터미널 편집기 `nano`로 고친다.

```bash
sudo nano /etc/systemd/system/myapp-backend.service
```

| 키 | 하는 일 |
|---|---|
| `Ctrl + O` → `Enter` | 저장 (write Out) |
| `Ctrl + X` | 나가기 |
| `Ctrl + K` | 한 줄 잘라내기 |
| `Ctrl + W` | 검색 |

화면 아래에 단축키가 항상 떠 있어서 `vi`보다 쉽다. 거기 적힌 `^O`의 `^`는 Ctrl을 뜻한다.

서버에서 직접 고치기 불편하면 로컬에서 고치고 git으로 push한 다음 서버에서 pull하는 방법이 있고(7/29 재배포 절차가 이 방식이다), VS Code의 Remote-SSH 확장으로 서버 파일을 로컬 화면에서 여는 방법도 있다. 다만 `/etc/nginx/...` 같은 시스템 설정은 어차피 서버에서 만져야 하니 `nano` 기본 조작은 알아둬야 한다.

## systemctl과 journalctl 맛보기
내일 자세히 나오지만 이름만 먼저 익혔다.

```bash
sudo systemctl status nginx              # 상태 확인
sudo systemctl restart nginx             # 재시작
sudo systemctl reload nginx              # 끊지 않고 설정만 다시 읽기
sudo systemctl enable nginx              # 부팅할 때 자동 시작 등록
sudo journalctl -u myapp-backend -n 50   # 최근 로그 50줄
```

`systemctl`은 서비스를 켜고 끄고 상태를 보는 리모컨이고, `journalctl`은 로그를 보는 창이다. `status` 결과에서는 한 줄만 보면 된다.

```
Active: active (running)     ← 정상
Active: failed               ← 죽었다. journalctl로 이유를 본다
```

`status` 출력이 길면 화면이 안 넘어가는데, 페이저(`less`)에 들어간 상태라 `q`를 누르면 빠져나온다. 처음부터 페이저를 안 쓰려면 `--no-pager`를 붙인다.

## 첫 배포 연습 - Hello 하나 띄우기
오늘 실습한 앱은 이게 전부다.

```python
# main.py
import uvicorn
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def root():
    return {"message": "Hello"}

if __name__ == "__main__":
    uvicorn.run("main:app", host="127.0.0.1", port=8000, reload=True)
```

```
# requirements.txt
fastapi==0.118.0
uvicorn==0.37.0
```

DB도 파일 업로드도 없이 일부러 최소한으로 만든 앱이다. 배포에서 뭔가 잘못됐을 때 앱 코드 문제인지 배포 문제인지 가려내려면 앱이 단순해야 한다.

코드는 git으로 서버에 가져온다.

```bash
git clone <저장소 주소> UpDown
cd UpDown/backend
```

여기서 첫 배포 때 꼭 걸리는 함정이 있다. 위 코드를 EC2에서 그대로 실행하고 브라우저로 `http://탄력적IP:8000`을 열면 아무 응답이 없다. 보안 그룹에 8000을 열어도 마찬가지다.

`127.0.0.1`은 "이 컴퓨터 자신"(loopback)이라는 뜻이라 서버 안에서만 접속이 된다. 확인은 서버 안에서 한다.

```bash
curl http://127.0.0.1:8000
# {"message":"Hello"}
```

밖에서 바로 보게 하려면 `host="0.0.0.0"`(모든 네트워크 인터페이스에서 받기)으로 바꾸고 보안 그룹에 8000을 열면 된다. 그런데 최종 구조에서는 `127.0.0.1`이 맞다. 내일 Nginx를 앞에 세워서 바깥(80/443) → Nginx → `127.0.0.1:8000`으로 넘기기 때문이다. 지금은 안 보이는 게 정상이고, 그걸 Nginx가 해결한다.

`reload=True`도 개발용이다. 파일이 바뀌면 서버를 자동으로 다시 띄워줘서 개발할 때는 편하지만, 운영에서는 파일 변경을 계속 감시하느라 자원을 쓰고 예상하지 못한 때에 재시작된다. 내일 Gunicorn으로 띄울 때는 이 옵션이 없고, 코드를 바꾸면 직접 재시작한다.

## AWS CLI는 직접 깔아야 한다
```bash
aws --version    # command not found면 설치 안 된 것
```

| AMI | AWS CLI |
|---|---|
| Amazon Linux 2 / 2023 | 미리 설치되어 있다 |
| Ubuntu, Debian | 직접 설치해야 한다 |

Ubuntu를 골랐으니 설치가 필요하다.

```bash
sudo apt update
sudo apt install unzip -y
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install
aws --version
```

설치했다고 바로 쓸 수 있는 건 아니고 인증 정보가 필요하다. 방법은 두 가지다.

| 방법 | 내용 | 평가 |
|---|---|---|
| `aws configure` | 액세스 키와 시크릿 키를 서버에 저장한다 | 키가 파일로 남는다 |
| IAM 역할(인스턴스 프로파일) | EC2에 역할을 붙이면 키 없이 동작한다 | 실무 권장 |

두 번째가 내일의 핵심 주제 중 하나다.

## 요금 사고를 막는 습관
프리 티어라도 방심하면 청구서가 온다.

- **Billing → Budgets**에서 예산 알림을 걸어둔다. 예를 들어 $5를 넘으면 메일이 오게 한다.
- 계속 요금이 나가는 것을 기억해둔다. RDS가 가장 비싸고, 놀고 있는 탄력적 IP, Route 53 호스팅 영역, NAT 게이트웨이도 요금이 나간다.
- EC2는 중지만 해도 컴퓨팅 요금은 멈추지만, 붙어 있는 디스크(EBS)와 탄력적 IP는 계속 요금이 나간다.
- AWS에 가입할 때 만든 루트 계정은 모든 권한을 가진 최상위 계정이라 MFA를 걸어두고 평소에는 쓰지 않는다. 대신 IAM 사용자를 만들어서 그걸로 로그인한다.

## 헷갈리기 쉬운 부분
- 리전이 서울이 아니면 만든 리소스가 목록에 안 보인다. "만들었는데 사라졌다"의 대부분이 이것이다.
- 인스턴스를 중지했다 켜면 퍼블릭 IP가 바뀐다. 도메인을 붙일 거라면 탄력적 IP가 필요하다.
- `.pem` 키는 다시 받을 수 없다. 잃어버리면 그 서버에 못 들어가고 인스턴스를 새로 만드는 수밖에 없다.
- SSH 규칙을 My IP로 걸어두면 집이나 학원처럼 장소가 바뀌어 내 IP가 달라졌을 때 접속이 막힌다. "어제 되던 SSH가 오늘 안 된다"의 1순위 원인이고, 보안 그룹에서 현재 IP로 다시 저장하면 된다.
- `Permission denied (publickey)`는 계정 이름을 틀렸을 때 흔히 나온다. Ubuntu는 `ubuntu`, Amazon Linux는 `ec2-user`다.
- IAM instance profile은 Advanced details 안에 숨어 있어서 펼치지 않으면 지나친다.
- 8000번 포트는 보안 그룹에 열지 않는다. 바깥 요청은 Nginx가 받아서 넘겨준다.
- `uv`를 깔았는데 `command not found`가 나오면 `source $HOME/.local/bin/env`를 빠뜨린 것이다.
- SSH 접속을 끊으면 `python main.py`로 띄운 서버도 같이 죽는다. 터미널에 붙어서 돌던 프로그램이라 터미널이 닫히면 같이 끝난다. 이걸 푸는 게 내일 배우는 systemd 등록이다.

## 오늘 배운 내용 정리
오늘은 EC2를 빌리고, 보안 그룹으로 열 문을 정하고, SSH로 들어가서 서버를 준비했다.

```
EC2: 시간 단위로 빌리는 리눅스 컴퓨터. 리전이 서울(ap-northeast-2)인지 확인.
인스턴스 생성: AMI(Ubuntu 24.04) + 타입(t3.micro) + 키페어(.pem) + 보안 그룹.
탄력적 IP: 껐다 켜도 안 바뀌는 고정 주소. 실습이 끝나면 Release.
보안 그룹: 기본 전부 차단, 열 것만 적는다. 80/443 누구나, 22는 My IP.
RDS 보안 그룹: Source에 IP 대신 sec-group-ec2. 우리 EC2만 DB에 닿는다.
SSH: ssh -i 키.pem ubuntu@주소. 계정 이름은 AMI마다 다르다.
apt: update(목록) → install(설치). sudo는 시스템을 건드릴 때만.
uv: uv python install 3.12.5 로 패치 버전까지 고정. 설치는 uv pip install.
127.0.0.1: 서버 자신만 닿는 주소. 서버 안에서 curl로 확인하고, 바깥은 Nginx가 맡는다.
```

로컬에서는 설치 프로그램 하나로 끝나던 일을 서버에서는 전부 명령으로 다시 해야 했다. 그중에서 보안 그룹 Source에 IP 대신 다른 보안 그룹을 넣어서 EC2만 DB에 들어갈 수 있게 만드는 방식이 가장 기억에 남았다. 내일은 오늘 띄운 FastAPI 앞에 Nginx를 세우고, SSH를 끊어도 서버가 계속 돌게 만든다.
